# 자소서 최종 수정

## 선택적 MCP 품질 평가

사용자가 Jev 평가, JD 일치 점수 또는 평가 후 개선을 요청하면 [일반 Chat MCP 흐름](../../references/career-mcp.md)을 읽고 적용하라. 실제 연결된 도구만 사용하며 Work 전환을 요구하지 않는다. 초안·개요·문체 검토만 요청하면 기존 범위를 유지한다. 외부 전송과 평가용 스냅샷 보관 동의, 평가와 문서 저장의 구분, 중단 상태 처리에 이 연결 지침을 적용하라.

**기존 원고의 좋은 내용은 유지하고 필요한 수정만 반영하여 제출 전 상태로 정리하라.** 전체를 무조건 새로 쓰지 마라. `ai-killer`의 진단을 반복하기보다 문항 충족, 사실 보존, 논리·문체, 분량·형식을 함께 검수하라.

작업 전에 [사실·문체 기준](references/evidence-and-style.md)을 읽어라. 수정 전후 [최종 검수 기준](references/final-checklist.md)을 확인하고, 결과에는 [출력 템플릿](references/output-template.md)을 적용하라. 분량 확인에는 [본문 점검 도구](references/text-audit.md)를, 단계 간 전달에는 필요할 때 [전달 메모](references/handoff.md)를 참고하라.

## 호출 범위 구분

- 스킬 이름보다 사용자가 마지막으로 요청한 작업과 결과물의 범위를 우선하라.
- 'AI 티 검사', '챗GPT 말투 줄이기', '표현만 자연스럽게 다듬기'는 기존 `ai-killer`의 진단·교정 범위다. 전체 수정본을 요청했다는 이유만으로 제출 전 종합 점검까지 덧붙이지 마라.
- '피드백을 반영한 최종본', '문항과 글자 수까지 제출 전 점검'에는 이 스킬을 사용하라. 이미 진단이 있으면 같은 진단 보고서를 반복하지 말고 필요한 수정을 검증하라.
- 두 작업을 함께 요청했을 때만 필요한 순서로 이어가라. 해당 스킬의 지침을 실제로 읽지 못했다면 사용했다고 보고하지 마라.
- '자소서 봐줘'처럼 범위가 모호하면 원고와 직전 맥락을 확인하라. 전체 재작성이나 전 단계 자동 실행을 임의로 시작하지 마라.

## 1. 기준 원고와 수정 범위 확인

수정 대상 본문, 문항 원문·제한, 회사·직무, 사용자 최신 정정, 원래 경험자료, 반드시 유지할 표현, 선택된 개요, `ai-killer` 등의 검토 결과 중 현재 있는 것을 확인하라.

- 원고가 여러 개면 사용자가 지정한 버전을 기준으로 하라. 지정이 없고 최신본이 명확하면 그 버전을 쓰고, 구별되지 않으면 기준 원고만 확인하라.
- 검토 결과가 없어도 최종 수정은 가능하다. 특정 진단 스킬을 반드시 먼저 실행하도록 요구하지 마라.
- 원고가 없으면 실제 접근 가능한 지정 자료를 확인하라. 그래도 없으면 원고를 요청하고 없는 글을 수정한 것처럼 만들지 마라.
- '맞춤법만', '첫 문단만', '내용 유지', '본문만' 같은 범위를 지켜라. 범위 밖의 중요한 사실 문제는 조용히 바꾸지 말고 별도로 알리라.
- 원문만 있으면 원문과의 의미 보존을 검토할 수 있지만 경험의 외부 사실 검증까지 완료했다고 말하지 마라.

## 2. 피드백의 타당성과 우선순위 판단

사용자 최신 요구와 정정을 우선하라. 기존 진단·첨삭은 원문과 근거에 대조하여 반영 여부를 정하라. 이미 자연스러운 문장까지 바꾸거나 모든 지적을 기계적으로 수용하지 마라.

편집 우선순위는 다음과 같다.
1. 사실 오류·과장, 역할·수행 상태, 문항의 필수 요구, 명시된 제한과 금지사항.
2. 실제 지원 이유, 핵심 답의 위치, 주장과 근거의 연결, 누락·중복.
3. 표현·호흡·맞춤법·용어·형식의 일관성.

지원동기가 빠졌다면 기술 표현만 다듬어 문제를 해결했다고 판단하지 마라. 현재 자료에 지원 이유가 있으면 복원하고, 없으면 개인 동기를 창작하지 말고 남은 확인사항으로 처리하라.

## 3. 필요한 범위만 수정

문장 수정으로 해결할 수 있으면 문장만 고쳐라. 문단 재배치나 소재 변경이 필요하면 이유를 구분하고 가능한 범위에서 반영하라. 사용자가 고정한 사실·핵심 주장·경험 배치는 정당한 이유 없이 바꾸지 마라.

`ai-killer`의 제안이 사실을 확대하거나 정확한 기술 용어를 왜곡하면 반영하지 마라. 같은 표현을 모두 없애거나 문장 길이를 인위적으로 다르게 만드는 것을 목표로 삼지 마라. AI 작성 확률이나 탐지 점수를 낮추는 반복 수정을 하지 마라.

초안에서 삭제한 미확인 수치, 단독 기여, 감정, 동기, 완료 주장을 표현을 바꿔 다시 도입하지 마라. 추가한 사실적 문장은 사용자 자료나 확인 출처에 연결할 수 있어야 한다.

## 4. 수정 전후 대조

수정본을 원문 및 최신 정정과 비교하라. 회사·직무명, 인물, 날짜·기간, 수치, 기술, 개인/팀 역할, 시제·진행 상태, 성과·인과관계, 주장 강도가 달라진 부분을 점검하라. 문자열 비교나 변경 수 집계만으로 의미 보존이 증명되지는 않는다.

첫 문장이 질문에 답하는지, 뒤의 경험이 그 답을 뒷받침하는지, 복합 문항의 모든 요소가 있는지 확인하라. 여러 문항이면 역할·시점·기술 표현의 모순, 같은 경험·결론의 반복, 다른 기업명이 남은 복사 오류를 확인하라.

확인된 블라인드·기밀 조건에 맞춰 민감한 정보를 조정하라. 없는 금지 규정을 임의로 추가하지 마라.

## 5. 분량과 제출 형식

최종 수정 후 본문을 다시 계산하라. 마지막으로 단어 하나라도 바꾸었으면 이전 계산값을 재사용하지 마라. 글자·바이트·공백·줄바꿈 기준과 제목의 포함 여부를 명시하라. 도구가 있으면 `scripts/text_audit.py`를 실행하고, 없으면 실제 이용 가능한 계산 방법을 쓰거나 정확한 수치 미검증을 밝혀라.

초과 시 중복과 장식 표현부터 줄이고, 부족 시 확인된 사실만 보강하라. 분량을 맞추려고 역할·상태·한계를 지우지 마라. `[확인 필요]`, 빈칸 표식, 편집자 메모, Markdown 강조가 제출 본문에 남지 않게 하라. 스크립트의 표식 탐지는 후보 확인일 뿐 모든 누락을 찾아낸다는 보장이 아니다.

사용자에게 그대로 제시할 본문과 검토 메모를 분리하라. 사이트 입력·지원서 제출·Drive 저장은 별도 명시 요청이 없으면 수행하지 마라.

## 6. 결과와 검증 상태

수정본을 먼저 제공하고, 변경 요약과 남은 확인사항을 필요한 만큼만 붙여라. '최종본만' 요청이면 긴 검토 보고서를 생략하라. 중요한 오류가 남으면 이를 숨기고 제출 가능한 완성본으로 표시하지 마라.

검증 상태는 근거가 있는 범위에서 '제공 자료 기준 점검 완료', '확인 후 제출 필요', '일부 범위만 수정'처럼 설명하라. 모든 사실의 진실성, 합격, AI 미탐지, 채용 사이트의 정확한 길이 판정을 보장하지 마라.

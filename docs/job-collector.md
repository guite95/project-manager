# 채용 공고 수집 워커

첫 구현은 공개 HTML·사이트맵 수집, IT 키워드 필터, PostgreSQL 저장, 매일 한국 시간
20시 예약 실행, CLI 조회와 채용 메뉴의 공고 목록을 제공한다. 경험 문서를 활용한 적합성 평가는 후속 범위다.
현재 환경의 외부 네트워크 제한으로 실제 사이트 HTML 호환성과 운영 실행은 검증하지 않았다.

## 수집원과 데이터 범위

- 예제 설정은 직행 공개 사이트맵을 시작점으로 사용한다. API·로그인·회원 전용 경로는 요청하지 않는다.
- 사람인·잡코리아·원티드·직행·자소설닷컴의 도메인과 공고 URL 형식을 등록했다.
  이것은 각 사이트의 수집 완료/호환성 인증이 아니다. 직행 외 시작 URL은 설정에 명시해야 한다.
- 잡플래닛은 무단 수집 금지 안내 때문에 수집원 목록에 넣지 않았다.
- 사이트마다 실행 시 robots.txt를 읽는다. 확인 실패와 접근 제한을 허용으로 처리하지 않는다.
  robots 규칙 외에 이용약관·저장 및 재사용 범위는 실제 활성화 전에 확인한다.
- HTTP 요청 사이에 기본 2초를 두고, Crawl-delay가 더 크면 따른다. 401/403/429는 해당 수집 회차를 중단한다.
  다른 호스트·API 경로로의 리디렉션은 차단한다. 응답은 2 MiB, 페이지 수와 공고 페이지 수는 설정 상한을 적용한다.
- JSON-LD JobPosting을 우선 읽는다. 한 페이지에 여러 JobPosting이 있으면 개별 직무로 저장한다.
  구조화 데이터가 없으면 h1과 main/article의 텍스트만 보존하며 회사·경력·마감 조건은 추정하지 않는다.
  이미지 전용 공고와 스크립트 실행 후에만 나오는 데이터는 이 버전에서 해석하지 않는다.
- `detailStatus`는 `AVAILABLE`(구조화 본문 있음), `MISSING`(본문 없음),
  `UNVERIFIED`(페이지 텍스트)이다. 키워드 일치는 지원 자격이나 개인 적합성 판정이 아니다.
- 사이트 내 공고 URL과 직무 식별자로 중복 저장을 막는다. 사이트 간 동일 공고는 아직 자동 병합하지 않는다.
- 수집 실패·목록에서 사라짐을 마감으로 처리하지 않는다. 명시된 validThrough만으로 마감 여부를 계산한다.
  날짜만 있으면 한국 시간 해당일 23:59:59로 해석하고, 시간대가 빠진 시각은 미확인으로 남긴다.
- 페이지/공고 상한에 걸리면 `PARTIAL`과 남은 URL 수를 표시한다. 대기열을 다음 회차에 이어서 읽는다.
  대기열 상한은 10,000개이며 초과하면 `queueTruncated=true`를 기록한다. 사이트 전체 수집을 보장하지 않는다.

## 설정과 실행

설정 예제는 `config/jobs-worker.example.json`이다. `keywords` 중 하나라도 제목/본문에
있으면 보관한다. 빈 배열이면 모든 직무를 보관한다. 경력 연수·지역을 임의로 가정하지 않는다.
설정에는 API 키, 쿠키, 이력서, 연락처, 고객 자료를 넣지 않는다.

```bash
# DB·외부 사이트에 접근하지 않고 설정과 다음 실행 시간을 확인한다.
pnpm jobs:worker inspect --config config/jobs-worker.example.json

# 공개 사이트 수집 미리보기. DB에 연결하거나 저장하지 않는다.
pnpm jobs:worker collect --config config/jobs-worker.example.json

# 공유 DB 저장 활성화가 승인된 이후의 1회 실행
pnpm db:shared -- pnpm jobs:worker collect --config config/jobs-worker.example.json --apply

# 매일 20:00 Asia/Seoul 예약 + 화면에서 요청한 수동 수집. 계속 실행되는 프로세스다.
pnpm db:shared -- pnpm jobs:worker watch --config config/jobs-worker.example.json --apply

# 읽기 전용 상태·공고 요약 확인
pnpm db:shared -- pnpm jobs:worker status
pnpm db:shared -- pnpm jobs:worker list --limit 50
```

`collect`는 기본 미리보기이며 `--apply`를 붙여야 저장한다. `watch`는 `--apply`가 필수다.
예약 판단은 UTC 서버에서도 한국 시간 기준이다. 30초 간격으로 확인하므로 실행은 20시부터
최대 약 30초 내에 시작한다. 20시 이후 프로세스를 시작하면 당일 미실행 회차를 처리하고,
20시 이전에는 기다린다. 이전 날짜의 누락 회차를 소급 실행하지 않는다.

실제 운영은 상시 가동되는 서버의 프로세스 관리가 필요하다. 이 CLI는 서비스·타이머를
설치하거나 배포하지 않는다. Docker 이미지에는 워커 실행 스크립트와 예제 설정을 포함하되
기본 웹 서버 시작 명령은 유지한다. 운영에서는 같은 이미지의 별도 프로세스로
`node scripts/jobs-worker.mjs watch --config <설정.json> --apply`를 실행하며 기존 런타임의 DB Secret을 사용한다.
현재 P-Grid security-principles 및 infrastructure-design-manual 원문 조회는 네트워크 제한으로
실패했다. 운영 등록 전에 최신 보안/인프라 매뉴얼과 기존 OCI 런타임 실행 경로를 확인한다.
공유 DB 최초 쓰기는 기존 키 검사·백업 후 별도 활성화 범위에서 수행한다.

## 채용공고 화면과 삭제

- 채용 → **채용공고** (`/recruitment/jobs`)에서 공고명·회사·지역 검색, 사이트·모집 상태 필터,
  30개씩 페이지 이동, 원문 열기, 선택한 공고의 본문 확인과 삭제를 제공한다.
- 화면과 `/api/recruitment/jobs`, `/api/recruitment/jobs/[id]`는 OWNER 전용이다.
  DELETE는 같은 출처의 JSON 요청만 허용한다. 목록 응답에는 본문을 포함하지 않는다.
  조회는 데이터를 생성하지 않으며, 저장된 공고가 없으면 빈 목록을 보여 준다.
- 삭제 확인 후 같은 사이트·정규화된 원문 URL의 모든 직무를 함께 삭제한다.
  본문은 제거하고 출처·주소·삭제 시각만 영구 제외 키로 남긴다. 복원 기능은 제공하지 않는다.
  공고 제목·본문·직무 식별자나 추출 방식이 바뀌어도 동일한 원문 URL이면 다시 저장하지 않는다.
- 삭제와 수집은 같은 원문 URL의 트랜잭션 advisory lock을 사용한다. 먼저 수집된 공고는 삭제가
  제거하고, 먼저 삭제된 공고는 수집기가 제외 키를 확인해 건너뛴다. 목록과 상세도 제외 키를 확인한다.
  회차 결과의 `stored`와 `excluded`로 저장/제외 건수를 구분한다.
- 다른 URL로 재등록된 공고와 다른 사이트의 공고는 별도로 취급한다. 회사·제목 유사성만으로
  자동 병합하거나 제외하지 않는다. 사이트 간 중복 판별은 후속 범위다.
- 목록은 창 포커스 복귀 및 화면이 보이는 동안 15초마다 갱신한다. 삭제 전에 시작한 조회 결과가
  늦게 도착해도 화면에 되살리지 않는다. 실제 수집은 워커 활성화가 필요하며 화면 조회가 수집을 실행하지 않는다.

## 수동 수집

- 채용공고 상단의 **지금 수집**은 `POST /api/recruitment/jobs/collect`로 실행 요청만 저장한다.
  OWNER와 같은 출처의 빈 JSON 요청이 필요하다. URL·설정·실행 명령을 브라우저에서 받지 않는다.
  접수 응답은 `202`이며, 완료 응답이 아니다. 요청은 DB에 남아 화면을 닫아도 유지된다.
- `watch --apply` 워커가 30초마다 요청을 확인한다. 워커가 꺼져 있으면 대기하며, 다시 실행하면
  요청을 처리한다. 정기 수집이 진행 중이면 끝난 뒤 처리하고, 수동 수집도 오후 8시 예약을 취소하거나 변경하지 않는다.
- 대기 또는 실행 중인 수동 요청은 하나만 유지한다. 연속 클릭·다른 탭의 동시 요청은 동일한 회차를 반환한다.
  수집원별 기존 lease도 적용하여 CLI 직접 수집이나 다른 워커와 같은 사이트를 동시에 수집하지 않는다.
- 요청 상태는 `QUEUED` → `RUNNING` → `SUCCESS` / `PARTIAL` / `FAILED`다.
  다른 실행이 수집원을 점유하고 있으면 `QUEUED`로 돌아가며, 다음 시도는 같은 회차에서 완료한 사이트의
  저장된 결과를 재사용한다. 오류나 중단을 정상 완료로 표시하지 않는다.
- 수동 요청의 5분 lease는 외부 요청 전과 저장 전에 갱신한다. 프로세스 중단 시 같은 회차로 최대 3회
  점유하며, 반복 중단 뒤에는 실패로 표시한다. 오래된 토큰은 상태를 덮어쓸 수 없다.
- `GET /api/recruitment/jobs/collect`는 최근 요청과 워커의 최근 활동을 읽으며 데이터를 생성하지 않는다.
  화면은 5초마다 상태를 확인하고 완료 후 공고 목록을 갱신한다. 90초 동안 활동이 확인되지 않은 워커는
  연결 미확인으로 표시한다. 응답과 CLI 상태 출력에는 lease 토큰을 포함하지 않는다.
- 터미널의 `collect --config <설정.json> --apply`도 즉시 수집을 지원한다. 이 직접 실행은 화면의
  수동 요청 대기열을 거치지 않으며, 사이트별 회차 기록과 중복·삭제 제외 규칙을 공유한다.

## 저장과 복구

기존 `app_setting`을 사용하므로 스키마 마이그레이션은 없다. 기존 채용 문서 키와 분리한다.

| 키 | 내용 |
| --- | --- |
| `recruitment:job:<sha256>` | 공개 공고의 정규화 내용, 출처 URL, 내용 해시, revision, 처음/최근 확인 시각, 사용자 상태 |
| `recruitment:job-exclusion:<sha256>` | 삭제한 원문의 사이트·정규화 URL·삭제 시각. 만료/자동 삭제 없음 |
| `recruitment:job-source:<source>` | 최신 실행 상태, DB 시각 기반 작업 점유, 다음 회차 대기열 |
| `recruitment:job-run:<source>:<runKey>` | 회차별 건수·상한 도달·오류 코드 |
| `recruitment:job-manual` | 최근 수동 요청, 실행 상태, DB 시각 기반 lease, 사이트별 결과 |
| `recruitment:job-worker` | 예약·수동 요청을 처리하는 watch 워커의 최근 활동 시각 |

한 수집원을 동시에 실행해도 5분 lease와 토큰으로 하나만 결과를 저장한다. HTTP 요청 전에
lease를 갱신하며, 저장 트랜잭션은 토큰과 만료를 다시 검사한다. 외부 호출은 트랜잭션 밖에서
실행하고 공고 저장·최종 회차 기록은 하나의 트랜잭션으로 처리한다.

예약 회차 키는 한국 날짜다. 정상 저장된 SUCCESS/PARTIAL/FAILED는 당일 반복하지 않는다.
프로세스 중단이나 저장 오류로 RUNNING이 남으면 lease 만료 후 동일 회차를 최대 3번 시도한다.
명시적 재시도는 `collect --apply`의 별도 manual 회차를 사용한다.

내용 해시가 같으면 revision은 증가하지 않는다. 수집기는 기존 `userState`와 `firstSeenAt`을
덮어쓰지 않는다. 조회는 DB를 변경하지 않으며 공고 목록에서 본문을 제외한다.
설정 변경은 과거 공고를 삭제하지 않는다. 오류 로그는 고정 코드만 쓰며 DB URL·쿠키·응답 원문을 출력하지 않는다.
본 수집기는 AI 대화/임베딩 워커나 비공개 경력 자료를 읽지 않고 LLM도 호출하지 않는다.

## 검증

```bash
node --experimental-strip-types --env-file-if-exists=.env --test lib/job-collector/*.test.mjs lib/recruitment-jobs.test.mjs lib/server/recruitment-jobs-http.test.mjs lib/access/policy.test.mjs lib/navigation/workspace-menu.test.mjs
pnpm typecheck
pnpm build
```

단위 테스트는 합성 HTML/XML/HTTP 응답으로 수집 경계, 본문 추출, 중복 식별자, 날짜,
20시 예약 유지, 수동 요청 처리·대기·재개·실패, 삭제 식별자, API 권한·출처 검증을 확인한다. DB 통합 테스트는
목록 필터·본문 분리, 동시 삭제/수집과 제목 변경 후 재수집 제외, 수동 요청의 동시 접수·단일 점유·토큰 만료를 검증하며, 기존 안전 장치가 허용하는
로컬 `localhost:5432/project_management_test`만 사용한다. 사이트 연결 확인과 운영 DB 확인은
단위 테스트 성공과 별도로 기록한다. 브라우저 검증은 명시 요청 시에만 수행한다.

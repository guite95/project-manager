# 채용 공고 수집 워커

공개 HTML·사이트맵·원티드 비로그인 JSON 목록 수집, IT 직군·신입~3년 지원 조건 필터, PostgreSQL 저장, 매일 한국 시간
20시 예약 실행, CLI 조회와 채용 메뉴의 공고 목록을 제공한다. 경험 문서를 활용한 적합성 평가는 후속 범위다.
운영 서버에서는 별도 상시 서비스가 예약 실행과 수동 요청을 처리한다. 웹 앱 이미지에
스크립트가 포함되어 있어도 이 서비스를 등록하지 않으면 수동 요청은 실행 대기에 남는다.

## 수집원과 데이터 범위

- 예제 설정은 직행 공개 채용 사이트맵을 먼저 읽고 전체 사이트맵을 탐색한다.
  전체 인덱스만 먼저 읽으면 수백 개의 하위 사이트맵이 공고 본문보다 먼저 대기열에 쌓여,
  초기 회차의 페이지 제한 안에 공고까지 도달하지 못한다. 로그인·회원 전용 경로는 요청하지 않는다.
- 예제 설정은 사람인·잡코리아·원티드·직행을 실행 대상으로 등록하고 자소설닷컴은 `DEFERRED`로 보류한다.
  설정 활성화는 수집 성공을 뜻하지 않는다. 사이트가 요청을 거부하면 해당 사이트만 실패로 기록한다.
  잡플래닛은 수집 대상에서 제외한다.
- 사이트마다 실행 시 robots.txt를 읽는다. 기본적으로 확인 실패는 중단한다.
  원티드에만 `allowRobots403: true`를 명시해 robots의 HTTP 403을 규칙 부재로 처리하며,
  `ROBOTS_HTTP_403_CONTINUED` 경고를 회차 결과와 화면에 남긴다.
  이는 [RFC 9309 2.3.1.3](https://www.rfc-editor.org/rfc/rfc9309.html#section-2.3.1.3)의 robots 4xx 처리에 따른 선택이다.
  받아 온 Disallow 규칙, robots 429/5xx/네트워크 오류, 실제 공고·목록의 401/403/429는 계속 중단한다.
  robots 규칙 외에 이용약관·저장 및 재사용 범위는 실제 활성화 전에 확인한다.
- HTTP 요청 사이에 기본 2초를 두고, Crawl-delay가 더 크면 따른다. 401/403/429는 해당 수집 회차를 중단한다.
  다른 호스트·미등록 API 경로로의 리디렉션은 차단한다. 응답은 2 MiB(사람인 검색 HTML만 4 MiB),
  페이지 수와 공고 페이지 수는 설정 상한을 적용한다.
- JSON-LD JobPosting을 우선 읽는다. 한 페이지에 여러 JobPosting이 있으면 개별 직무로 저장한다.
  구조화 데이터가 없으면 h1과 main/article의 텍스트만 보존하며 회사·경력·마감 조건은 추정하지 않는다.
  이미지 전용 공고와 스크립트 실행 후에만 나오는 데이터는 이 버전에서 해석하지 않는다.
- 잡코리아는 `/Search`의 IT 검색어별 목록과 `Page_No` 링크를 탐색하고, 상세 공개 HTML의
  Next.js 페이지 데이터에서 현재 `jobId`와 일치하는 공고의 경력·업무·마감일을 읽는다.
  사람인은 `/zf_user/search/recruit`의 `recruitPage`를 따라가고, 본문이 포함된 공개 `/zf_user/jobs/view`를
  요청한다. 저장 주소는 기존 `/relay/view?rec_idx=...`로 통일해 삭제 기록과 중복 판별을 유지한다.
  사람인 본문은 현재 ID의 `jobsViewDetail_<id>` 영역만 읽고 회사 소개·추천 공고는 포함하지 않는다.
  상세 본문을 읽지 못하면 공개 메타 요약만 저장하고 `UNVERIFIED`로 표시한다.
- 두 검색 목록은 현재 검색 조건을 유지한 바로 다음 페이지 하나만 대기열에 추가한다.
  검색어는 탐색 범위이며 최종 보관은 아래 공통 직군·연차 필터로 결정한다.
- 원티드 `/wdlist/518`의 HTML에는 공고가 없어, 같은 비로그인 화면이 사용하는
  `/api/chaos/navigation/v1/results` GET 한 경로만 허용한다. 개발(518)과 경영·비즈니스(507, IT 기획·데이터 분석 포함)
  목록을 20개씩 읽고, 같은 필터의 다음 offset만 따라간다. 다른 API·임의 쿼리·대량 limit는 거부한다.
  필터는 탐색 범위이며 사무·비IT 공고는 공통 판정에서 제외한다.
  상세는 `/wd/<id>` HTML의 `__NEXT_DATA__.props.pageProps.initialData`를 JSON으로 파싱한다.
  현재 ID의 연차·신입 여부·본문·마감 상태를 읽고, JSON-LD의 단순 `경력` 표기를 보완한다.
  `active`는 모집 중, `close` 또는 지난 명시 마감일은 마감으로 표시한다.
  이 JSON 목록은 공식 파트너 API가 아니므로 사이트 변경에 따라 연결 보완이 필요할 수 있다.
- `detailStatus`는 `AVAILABLE`(구조화 본문 있음), `MISSING`(본문 없음),
  `UNVERIFIED`(페이지 텍스트)이다. 키워드 일치는 지원 자격이나 개인 적합성 판정이 아니다.
- 사이트 내 공고 URL과 직무 식별자로 중복 저장을 막는다. 다른 사이트라도 명시된 원문·지원 링크가
  같은 등록된 공고 주소를 가리키면 목록에서 묶는다. 회사명·제목 유사성만으로는 병합하지 않는다.
  한 페이지의 여러 직무는 개별 항목을 유지한다. 연결 주소를 찾지 못하면 별도 공고로 남는다.
- 직행은 공개 HTML에 포함된 페이지 데이터에서도 현재 공고 ID에 해당하는 `redirectUrl`을 읽는다.
  스크립트 실행이나 내부 API 호출 없이 JSON만 파싱하며, 추천 공고의 지원 주소는 연결하지 않는다.
- 수집 실패·목록에서 사라짐을 마감으로 처리하지 않는다. 명시된 validThrough만으로 마감 여부를 계산한다.
  날짜만 있으면 한국 시간 해당일 23:59:59로 해석하고, 시간대가 빠진 시각은 미확인으로 남긴다.
- 페이지/공고 상한에 걸리면 `PARTIAL`과 남은 URL 수를 표시한다. 대기열을 다음 회차에 이어서 읽는다.
  대기열 상한은 10,000개이며 초과하면 `queueTruncated=true`를 기록한다. 사이트 전체 수집을 보장하지 않는다.

## 설정과 실행

설정 예제는 `config/jobs-worker.example.json`이다. 보관 여부는 아래 공통 직군·경력 기준으로 판단한다.
이전 운영 설정의 `keywords`는 호환성을 위해 일치 단어 기록에만 사용하며, 보관 여부를 결정하지 않는다.
경력 연수·지역을 임의로 가정하지 않는다.
설정에는 API 키, 쿠키, 이력서, 연락처, 고객 자료를 넣지 않는다.

### 직군과 경력 기준

- `lib/job-collector/eligibility.mjs`를 수집·저장·기존 목록 조회에서 함께 사용한다.
  개발, 인프라, 데이터, AI, QA, IT 기획, 기술지원, ERP·업무 시스템 등 IT 직군 전반을 포함한다.
  제목과 담당 업무를 판단하며 우대사항의 기술 단어만으로 통과시키지 않는다.
- 보안 직무, 단순 사무·전산입력·경리·자재관리, 출장 수리·현장 데이터복구는 제외한다.
  일반 개발의 인증·보안 강화 업무나 보안 회사라는 이유만으로 제외하지 않는다.
- 신입·경력무관 또는 필수 최소 경력 3년 이하를 포함한다. `3년 이상`, `2~5년`도
  3년 경력으로 지원 가능하므로 포함하고, `4년 이상`·`3년 초과`는 제외한다. `2년차~4년차`도 하한 2년으로 판정한다.
  필수 요건과 우대사항을 구분하며 구조화된 월 단위 경력도 연수로 변환한다.
- 경력 조건이 없거나 해석할 수 없으면 `REVIEW / EXPERIENCE_UNCONFIRMED`로 분류해
  목록에 표시하지 않는다. 신입사원 교육, 근속 포상, 회사 설립 연도는 지원 조건으로 해석하지 않는다.
  규칙 기반 판정이므로 표현이 새로운 공고는 추출/판정 규칙 보완이 필요할 수 있다.
- 신규 탈락 공고는 저장하지 않는다. 기존 공고는 조회 시 같은 기준으로 거른 후 전체 건수와 페이지를
  계산하며, GET으로 원문을 수정하거나 삭제하지 않는다. 재수집 중 기존 공고의 조건이 바뀌면
  원문과 판정만 갱신하고 사용자 상태·최초 수집일·영구 제외 기록은 보존한다.
- 판정 기준 버전이 바뀌면 기존 공고도 재평가한다. 현재 버전 판정이 없는 기존 공고 본문은
  서버 내부 재평가에만 읽으며 목록 API에는 포함하지 않는다.

### 다른 플랫폼 연결

도메인 등록만으로 실제 수집은 활성화되지 않는다. 플랫폼마다 허용되는 공개 목록/사이트맵 탐색,
공고 상세의 직무·필수 경력·마감 추출, 페이지 이동과 오류 처리 검증이 필요하다.
먼저 DB 저장 없는 소량 미리보기로 실제 공고가 파싱되는지와 누락 필드를 확인하고,
공통 필터·중복·영구 제외 검증 뒤 `sources` 설정을 운영 설치 절차로 반영한다.
robots 접근 허용만으로 저장·재사용 권한까지 확인된 것으로 간주하지 않는다.
사람인 API를 사용하는 경우에도 별도 API 커넥터가 필요하며 현재 HTML 커넥터에 키를 넣지 않는다.
워커 활동 정보와 수동 실행 결과에는 비활성 플랫폼의 `disabledReason`도 표시한다.
비활성 플랫폼은 HTTP 요청·DB 공고 저장을 하지 않고 `DISABLED`로 보고한다.
수동 실행은 수집하지 못한 플랫폼이 있으면 `PARTIAL`로 표시한다. 사용자가 보류한 `DEFERRED` 플랫폼은
요청하지 않으며, 나머지 플랫폼이 모두 성공하면 전체 `SUCCESS`를 유지한다.

2026-10-05 확인 결과:

| 플랫폼 | 연결 상태 | 근거 |
| --- | --- | --- |
| 직행 | 수집 확인 | 공개 사이트맵·상세 6건 파싱, 모두 비IT 직군으로 제외, 오류 0건 |
| 잡코리아 | 수집 확인 | 실제 검색 목록 1페이지·상세 6건 파싱, 2건 조건 통과·4건 제외, HTTP/파싱 오류 0건. 경력은 현재 공고 페이지 데이터에서 추출 |
| 사람인 | 수집 확인 | 실제 검색 목록·상세 6건 파싱, 4건 조건 통과·2건 제외, 본문 6건 확보, 오류 0건 |
| 원티드 | 수집 확인 | 비로그인 JSON 목록·상세 6건 파싱, 4건 직군·연차 통과(마감 1건 포함)·2건 연차 초과 제외. robots 403 경고 외 HTTP/파싱 오류 0건 |
| 자소설닷컴 | 사용자 요청으로 보류 | `enabled: false`, `disabledReason: DEFERRED`. 이번 검증에서 요청하지 않음 |

위 수집 건수는 DB 저장 없는 소량 검증 결과이며 전체 공고 수집이나 운영 반영을 의미하지 않는다.
잡코리아·사람인 검색과 원티드 JSON 목록의 2페이지에서 각각 새로운 공고 주소 20개를 확인했다.
원티드는 OCI 워커 컨테이너에서도 같은 User-Agent·무인증 GET으로 목록 HTTP 200(20건),
상세 HTTP 200 및 페이지 데이터 존재를 확인했다. 이는 연결 확인이며 새 코드 배포·DB 저장 검증은 아니다.
운영 워커 컨테이너에서도 두 사이트의 목록·상세에 HTTP 200을 확인했으며, 새 파서의 운영 배포는 별도다.
원티드·자소설은 접근 제한 해소 후 실제 목록·상세 형식과 페이지 이동을 재검증해야 한다.
원티드 [공식 OpenAPI 안내](https://openapi.wanted.jobs/guides/)는 발급받은 클라이언트 ID/secret을
요구한다. 현재 워커는 이 API를 사용하지 않는다. 인증·쿠키·프록시로 사이트 제한을 우회하지 않는다.
공개 페이지 기술 검증은 약관상 복제·저장·재사용 권한의 확인을 대신하지 않는다.

운영 반영에는 앱 이미지 배포와 호스트에 고정 마운트한 `jobs-worker.json`의 갱신이 모두 필요하다.
예제 설정을 커밋하거나 웹 앱만 배포해도 이전 직행 전용 운영 설정이 자동 변경되지는 않는다.

```bash
# DB·외부 사이트에 접근하지 않고 설정과 다음 실행 시간을 확인한다.
pnpm jobs:worker inspect --config config/jobs-worker.example.json

# 공개 사이트 수집 미리보기. DB에 연결하거나 저장하지 않는다.
pnpm jobs:worker collect --config config/jobs-worker.example.json

# 공유 DB 저장 활성화가 승인된 이후의 1회 실행
pnpm db:shared -- pnpm jobs:worker collect --config config/jobs-worker.example.json --apply

# 매일 20:00 Asia/Seoul 예약 + 화면에서 요청한 수동 수집. 계속 실행되는 프로세스다.
pnpm db:shared -- pnpm jobs:worker watch --config config/jobs-worker.example.json --apply

# 읽기 전용 상태·공고 요약 확인
pnpm db:shared -- pnpm jobs:worker status
pnpm db:shared -- pnpm jobs:worker list --limit 50
```

`collect`는 기본 미리보기이며 `--apply`를 붙여야 저장한다. `watch`는 `--apply`가 필수다.
예약 판단은 UTC 서버에서도 한국 시간 기준이다. 30초 간격으로 확인하므로 실행은 20시부터
최대 약 30초 내에 시작한다. 20시 이후 프로세스를 시작하면 당일 미실행 회차를 처리하고,
20시 이전에는 기다린다. 이전 날짜의 누락 회차를 소급 실행하지 않는다.

실제 운영은 상시 가동되는 서버의 프로세스 관리가 필요하다. 이 CLI는 서비스·타이머를
설치하거나 배포하지 않는다. Docker 이미지에는 워커 실행 스크립트와 예제 설정을 포함하되
기본 웹 서버 시작 명령은 유지한다. 운영에서는 같은 이미지의 별도 프로세스로
`node scripts/jobs-worker.mjs watch --config <설정.json> --apply`를 실행하며 기존 런타임의 DB Secret을 사용한다.
공유 DB 최초 쓰기는 기존 키 검사·백업 후 별도 활성화 범위에서 수행한다.

### OCI 상시 서비스

`project-management-jobs.service`는 오후 8시까지 기다리는 동안에도 실행 중이다.
`watch`가 30초마다 수동 요청을 처리하므로 오후 8시 전후와 관계없이 **지금 수집**을 사용할 수 있다.
서버 부팅 때 자동 시작하며 종료되면 systemd가 다시 시작한다.

```bash
# 로컬: 설치할 파일과 해시만 확인한다. SSH/DB 접근 없음.
python3 ops/oci-runtime/install-jobs-worker.py

# 운영 활성화 범위: 기존 개인 SSH로 백업·검증 후 채용 서비스만 설치/시작한다.
python3 ops/oci-runtime/install-jobs-worker.py --apply

# 서버: 읽기 전용 상태 확인
systemctl is-active project-management-jobs.service
docker exec project-management-jobs node scripts/jobs-worker.mjs status
sudo python3 /opt/project-management-jobs/current/jobs-worker-runtime.py verify

# 서버: 채용 워커만 중지하고 자동 시작 해제. 기존 요청/공고/제외 기록은 보존한다.
sudo systemctl disable --now project-management-jobs.service
```

설치기는 `recruitment:job%` 키 전체를 서버의 root 전용
`/var/backups/project-management-jobs/<timestamp>/job-settings.json`에 저장하고 해시를 재검증한다.
DB 비밀번호는 기존 앱 컨테이너 안에서만 읽고 백업에는 포함하지 않는다. DB 스키마 변경은 없다.
이미 실행 중인 워커는 자동 교체하지 않는다. 설정/서비스 갱신 시 먼저 해당 서비스만 명시적으로 중지한다.

실행 파일과 설정은 `/opt/project-management-jobs/releases/<sha256>`에 보관한다.
워커는 현재 웹 앱과 동일한 immutable image digest로 별도 컨테이너를 만든다.
설치 시 예제 설정을 고정한 `jobs-worker.json`을 읽기 전용 마운트하므로 이후 설정 변경도 설치기를 통해 반영한다.
사용자는 1000:1000, 기존 `pm-runtime` 그룹과 private Docker 네트워크를 사용한다.
기존 런타임 Secret과 공용 수집 설정만 읽기 전용으로 마운트하며 포트를 노출하지 않는다.
IMDS 차단과 Vault 준비 상태를 먼저 확인하고, 권한·메모리·CPU·프로세스 수를 제한한다.
Google 인증, migration Secret, Docker socket을 전달하지 않는다.

서비스는 웹 런타임의 `PartOf`/`WantedBy` 관계로 함께 중지·시작된다.
이후 기존 배포 절차가 웹 런타임을 교체해 시작하면, 중지된 소유 컨테이너만 새 앱 이미지로 재생성한다.
이름만 같은 외부 컨테이너는 제거하지 않는다. 최초 등록은 기존 웹 앱과 녹음 워커를 재시작하지 않는다.
실행 중단 시 요청과 수집 lease는 기존 만료/재개 규칙을 따른다.

## 채용공고 화면과 작성 완료·삭제

- 채용 → **채용공고** (`/recruitment/jobs`)에서 공고명·회사·지역 검색, 사이트·모집 상태 필터,
  30개씩 페이지 이동, 원문 열기, 선택한 공고의 본문 확인, 자소서 작성 완료와 삭제를 제공한다.
- 화면과 `/api/recruitment/jobs`, `/api/recruitment/jobs/[id]`는 OWNER 전용이다.
  PATCH·DELETE는 같은 출처의 JSON 요청만 허용한다. 목록 응답에는 본문을 포함하지 않는다.
  조회는 데이터를 생성하지 않으며, 저장된 공고가 없으면 빈 목록을 보여 준다.
- 공고의 **자소서 작성 완료** 버튼은 확인창 없이 `PATCH /api/recruitment/jobs/[id]`로
  `userState: COVER_LETTER_WRITTEN`을 저장한다. 공고 본문은 보관하고 작성 완료 시각을 기록하며,
  삭제 제외 키는 만들지 않는다. 같은 원문으로 연결된 다른 플랫폼 사본과 직무도 함께 처리한다.
  반복 요청은 작성 완료 시각·revision을 바꾸지 않고, 수집과 동일한 쓰기 잠금으로 갱신 충돌을 방지한다.
- 작성 완료 공고와 연결된 사본은 검색·사이트·모집 상태 필터와 페이지 계산 전에 목록에서 제외한다.
  재수집으로 ID·제목이 바뀌거나 새 플랫폼 사본이 추가되어도 보관된 완료 공고와 원문 연결이 확인되면 숨긴다.
  검색 조건 밖의 완료 공고도 연결 판단에 사용하며, 조회 과정에서 상태를 저장하거나 공고를 삭제하지 않는다.
- 삭제 확인 후 정규화된 원문 URL과 연결된 다른 플랫폼 사본의 모든 직무를 함께 삭제한다.
  본문은 제거하고 출처·주소·삭제 시각·식별 기준 버전만 영구 제외 키로 남긴다. 복원 기능은 제공하지 않는다.
  공고 제목·본문·직무 식별자나 추출 방식이 바뀌어도 동일한 원문 URL이면 다시 저장하지 않는다.
- 삭제와 수집은 플랫폼 공통 쓰기 잠금과 원문 URL의 트랜잭션 advisory lock을 사용한다. 먼저 수집된 공고는 삭제가
  제거하고, 먼저 삭제된 공고는 수집기가 제외 키를 확인해 건너뛴다. 목록과 상세도 제외 키를 확인한다.
  회차 결과의 `stored`와 `excluded`로 저장/제외 건수를 구분한다.
- 연결 근거가 없는 다른 URL의 공고는 별도로 취급한다. 회사·제목 유사성만으로 자동 삭제하지 않는다.
  기존 공고·삭제 기록의 식별 버전이 오래되면 다음 수집에서 해당 주소를 먼저 다시 읽는다.
  삭제 원문을 다시 읽어도 본문은 저장하지 않고 확인된 원문 주소의 제외 기록만 확장한다.
- 목록은 창 포커스 복귀 및 화면이 보이는 동안 15초마다 갱신한다. 삭제·작성 완료 전에 시작한 조회 결과가
  늦게 도착해도 화면에 되살리지 않는다. 실제 수집은 워커 활성화가 필요하며 화면 조회가 수집을 실행하지 않는다.

## 수동 수집

- 채용공고 상단의 **지금 수집**은 `POST /api/recruitment/jobs/collect`로 실행 요청만 저장한다.
  OWNER와 같은 출처의 빈 JSON 요청이 필요하다. URL·설정·실행 명령을 브라우저에서 받지 않는다.
  접수 응답은 `202`이며, 완료 응답이 아니다. 요청은 DB에 남아 화면을 닫아도 유지된다.
- `watch --apply` 워커가 30초마다 요청을 확인한다. 워커가 꺼져 있으면 대기하며, 다시 실행하면
  요청을 처리한다. 정기 수집이 진행 중이면 끝난 뒤 처리하고, 수동 수집도 오후 8시 예약을 취소하거나 변경하지 않는다.
- 대기 또는 실행 중인 수동 요청은 하나만 유지한다. 연속 클릭·다른 탭의 동시 요청은 동일한 회차를 반환한다.
  수집원별 기존 lease도 적용하여 CLI 직접 수집이나 다른 워커와 같은 사이트를 동시에 수집하지 않는다.
- 요청 상태는 `QUEUED` → `RUNNING` → `SUCCESS` / `PARTIAL` / `FAILED`다.
  일부 사이트에서 수집하고 나머지는 접근 실패한 경우 `PARTIAL`로 표시한다.
  사이트별 저장 건수, 접근 제한 사유, 수집 상한 도달 여부를 함께 표시한다.
  다른 실행이 수집원을 점유하고 있으면 `QUEUED`로 돌아가며, 다음 시도는 같은 회차에서 완료한 사이트의
  저장된 결과를 재사용한다. 오류나 중단을 정상 완료로 표시하지 않는다.
- 수동 요청의 5분 lease는 외부 요청 전과 저장 전에 갱신한다. 프로세스 중단 시 같은 회차로 최대 3회
  점유하며, 반복 중단 뒤에는 실패로 표시한다. 오래된 토큰은 상태를 덮어쓸 수 없다.
- `GET /api/recruitment/jobs/collect`는 최근 요청과 워커의 최근 활동을 읽으며 데이터를 생성하지 않는다.
  화면은 5초마다 상태를 확인하고 완료 후 공고 목록을 갱신한다. 90초 동안 활동이 확인되지 않은 워커는
  연결 미확인으로 표시한다. 응답과 CLI 상태 출력에는 lease 토큰을 포함하지 않는다.
- 터미널의 `collect --config <설정.json> --apply`도 즉시 수집을 지원한다. 이 직접 실행은 화면의
  수동 요청 대기열을 거치지 않으며, 사이트별 회차 기록과 중복·삭제 제외 규칙을 공유한다.

## 저장과 복구

기존 `app_setting`을 사용하므로 스키마 마이그레이션은 없다. 기존 채용 문서 키와 분리한다.

| 키 | 내용 |
| --- | --- |
| `recruitment:job:<sha256>` | 공개 공고의 정규화 내용, 출처 URL, 내용 해시, revision, 처음/최근 확인 시각, 사용자 상태 |
| `recruitment:job-exclusion:<sha256>` | 삭제한 원문의 사이트·정규화 URL·삭제 시각·식별 기준 버전. 만료/자동 삭제 없음 |
| `recruitment:job-source:<source>` | 최신 실행 상태, DB 시각 기반 작업 점유, 다음 회차 대기열 |
| `recruitment:job-run:<source>:<runKey>` | 회차별 건수·상한 도달·오류 코드 |
| `recruitment:job-manual` | 최근 수동 요청, 실행 상태, DB 시각 기반 lease, 사이트별 결과 |
| `recruitment:job-worker` | 예약·수동 요청을 처리하는 watch 워커의 최근 활동 시각 |

한 수집원을 동시에 실행해도 5분 lease와 토큰으로 하나만 결과를 저장한다. HTTP 요청 전에
lease를 갱신하며, 저장 트랜잭션은 토큰과 만료를 다시 검사한다. 외부 호출은 트랜잭션 밖에서
실행하고 공고 저장·최종 회차 기록은 하나의 트랜잭션으로 처리한다.

예약 회차 키는 한국 날짜다. 정상 저장된 SUCCESS/PARTIAL/FAILED는 당일 반복하지 않는다.
프로세스 중단이나 저장 오류로 RUNNING이 남으면 lease 만료 후 동일 회차를 최대 3번 시도한다.
명시적 재시도는 `collect --apply`의 별도 manual 회차를 사용한다.

내용 해시가 같으면 revision은 증가하지 않는다. 수집기는 기존 `userState`와 `firstSeenAt`을
덮어쓰지 않는다. 조회는 DB를 변경하지 않으며 공고 목록에서 본문을 제외한다.
설정 변경은 과거 공고를 삭제하지 않는다. 오류 로그는 고정 코드만 쓰며 DB URL·쿠키·응답 원문을 출력하지 않는다.
본 수집기는 AI 대화/임베딩 워커나 비공개 경력 자료를 읽지 않고 LLM도 호출하지 않는다.

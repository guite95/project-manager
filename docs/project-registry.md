# 프로젝트 목록과 저장소 연결

풀링(회사)과 개인 프로젝트 모두 `flow_project`가 메뉴의 기준이다. 이름과 순서 외에 `scope`(`COMPANY`/`PERSONAL`), `personal_group`(`PORTFOLIO`/`TOY`), 편집 충돌 방지용 `revision`을 저장한다. 개인 분류만 개인 프로젝트에 존재할 수 있도록 DB CHECK가 제한한다. 사이드바 사용자 순서는 기존 `app_setting`의 `sidebar:project-order`를 계속 사용한다.

저장소는 `project_repository`에 프로젝트 FK와 작업 폴더(`UK` = `~/uk`, `PROJECTS` = `~/Documents/project`), 상대 경로를 저장한다. 한 프로젝트에 여러 저장소를 연결할 수 있으며 같은 작업 폴더/경로를 다른 프로젝트에 중복 연결할 수 없다. 절대 경로, 상위 디렉터리 이동, 시크릿은 저장하지 않는다.

## 화면

- 개인 첫 화면: **프로젝트 추가**에서 등록하고, 각 프로젝트의 **기록 → 프로젝트 수정**에서 이름과 저장소 연결을 변경한다. 새 프로젝트 등록 때 포폴용/토이를 선택한다. 전체 프로젝트 목록은 표시하지 않는다.
- 풀링의 전체 프로젝트: 같은 추가/수정 기능을 제공한다. 포폴용/토이 분류는 없다.
- 소유자는 둘 다 관리할 수 있다. 관리자는 회사 프로젝트만 추가/수정할 수 있고, 멤버는 프로젝트 목록을 관리할 수 없다. 회사/개인 소속은 등록 후 일반 수정으로 변경하지 않는다.
- 사이드바 드래그 및 방향키 이동으로 개인 분류를 변경할 수 있다. 분류 API는 실제 DB의 개인 프로젝트만 갱신한다. GET은 등록이나 설정 생성을 하지 않는다.
- 저장 후 메뉴가 새로고침된다. 다른 열린 화면의 메뉴는 창 복귀 및 15초 간격 조회로 변경을 읽는다.

`POST/PATCH /api/project-registry`는 현재 서버 세션을 검증한다. 수정은 revision을 비교하며 저장소 충돌 시 이름 변경까지 롤백한다. 읽기/쓰기 권한, 공개 공유 제한, 메뉴·검색·개인 이슈 구분은 동일한 DB scope를 사용한다. 개인 프로젝트의 기존 개별 멤버십은 보존한다.

## Git 수집

work-sum은 DB에서 프로젝트별 저장소 목록을 읽어 로컬 Git 수집에 전달한다. 명시적 `--mapping`이 최우선이며, 그다음 DB 저장소 연결, 마지막으로 기존 프로젝트 slug 경로 구간 일치 규칙을 적용한다. 추가 워크트리는 공통 Git 디렉터리로 같은 프로젝트에 연결된다. AI 대화 조회나 임베딩 재개와는 관계없다.

## 최초 전환 순서

1. 공유 DB를 읽기 전용으로 조사하고 백업한다. `20260922090000_project_registry`를 로컬 테스트 DB에서 먼저 검증한다.
2. 승인된 운영 반영 때 커밋된 배포 이미지와 기존 `ops/oci-runtime/migrate-pm.mjs` 경로로 `prisma migrate deploy`를 실행하고 새 앱을 배포한다. 공유 DB 터널의 앱 계정에는 DDL 권한이 없으므로 `pnpm db:shared:deploy`로 우회하지 않는다. 마이그레이션은 기존 프로젝트/자료/메모/멤버십을 삭제하지 않는다. 등록돼 있는 개인 프로젝트의 scope와 기존 공유 분류를 이관하고, 기존 `ui:personal-project-groups`는 이관 근거로 보존한다.
3. 새 앱 배포가 확인된 뒤 `scripts/register-personal-projects.mjs inspect`로 남은 최초 등록 목록을 확인하고, `apply --backup-dir <dir>`로 요청한 콘끼리·메모노기·youtube-sync를 등록한다. 공유 DB apply는 운영 이미지의 DB 기반 등록 기능을 확인해야 실행된다.
4. DB의 프로젝트·분류·저장소와 기존 내용/권한 보존을 재조회한다. 이후 프로젝트 추가/수정은 화면에서 수행하며 코드 목록 변경이나 재배포가 필요 없다.

`scripts/personal-project-seed.mjs`는 최초 전환 때 요청받은 목록만 담는다. 런타임 메뉴·권한·Git 수집에서는 읽지 않는다. 기존 이름과 다른 임의의 이름을 초기 등록 스크립트가 덮어쓰지 않도록 충돌 시 중단한다.

새 스키마는 구버전 앱이 사용하는 컬럼을 보존하지만, 구버전 앱은 새 개인 프로젝트를 구분할 수 없다. 따라서 새 프로젝트를 추가한 뒤 구버전 이미지로 롤백하려면 별도 호환성 검토가 필요하다. 분류는 전환 후 DB 컬럼만 갱신하므로 구버전 앱과 신버전 앱을 장기간 병행하지 않는다.

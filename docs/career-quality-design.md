# 자기소개서 품질 평가 · 1단계 설계

작성일: 2026-09-29 · 설계 버전: `career-quality/0.1.0` · 상태: 기준 설계. 첫 로컬 구현 범위·제한·운영 준비는 [런타임 문서](career-quality-runtime.md)를 따른다.

## 목적과 범위

일반 ChatGPT Chat에서 기존 `career-application-toolkit` 플러그인으로 작성하고, 원격 MCP를 통해 JD·경험 근거·원고를 평가한다. ChatGPT는 작성과 수정, Jev는 정해진 질문의 판정, 서버는 정확한 계산과 버전·반복 제어를 담당한다.

이번 단계는 평가표와 [데이터 규약](career-quality-contract.md)을 정의한다. MCP 구현, OAuth, DB 저장 구조, 서버 배포, 플러그인 게시와 실데이터 평가는 다음 단계의 작업이다. 이 문서의 기준은 기업의 공식 채점표나 합격·AI 작성 확률이 아니다. 점수와 임계값은 한국어 자기소개서로 검증하기 전 초기 설정이다.

기준 자료는 사용자가 제공한 `plugin.zip`의 0.2.0 스킬 5개와 공통 사실·문체 지침이다. 예시는 모두 가상이며 실제 지원자 자료를 저장소에 넣지 않는다.

## 평가를 세 층으로 구분

1. **지원 조건·경험 매칭:** 실제 경험·자격이 JD 요구에 부합하는지 판단한다. 문장을 고친다고 경험이 달라지지 않는다.
2. **필수 확인:** 문항 누락, 근거 없는 주장, 모순, 분량·명시된 형식 위반을 확인한다. 총점으로 상쇄하지 않는다.
3. **글의 품질:** 문항 답변, JD 연결, 구성·구체성·문장 표현을 평가한다. 충분한 근거가 있는 부분만 수정한다.

### JD 요구사항 처리

- 요구사항을 `ELIGIBILITY`(지원 조건), `DUTY`(담당 업무), `COMPETENCY`(역량)로 분류하고 필수·우대·미명시를 별도로 보존한다.
- 원문 인용과 위치를 남긴다. 필수 조건의 AND/OR와 대체 인정 조건을 논리식으로 보존한다.
- 요구사항별 결과는 `MET`, `PARTIAL`, `NOT_MET`, `UNKNOWN`이다. 근거 자료에 언급이 없으면 `UNKNOWN`이다.
- `NOT_MET`는 확인된 사실이 요구 조건에 못 미칠 때만 사용한다. 기술 경험을 경력 연수·운영 규모로 확대하지 않는다.
- 경험은 충족하나 원고 설명이 약하면 글 수정 대상이다. 실제 경험이 부족하면 확인사항으로 반환한다.
- 원고에 JD의 모든 항목을 넣도록 강제하지 않는다. 각 문항에 관련된 요구사항만 평가한다. 협업 문항에 모든 기술을 나열할 필요는 없다.
- 지원 조건 미충족이 글 작성 자체를 막지는 않는다. 조건 매칭 결과와 글의 품질 결과를 함께 보여준다.

### 필수 확인 항목

| ID | 확인 내용 | 담당 | 실패·불확실 시 처리 |
| --- | --- | --- | --- |
| G1 | 문항의 필수 하위 질문에 답했는가 | Jev + 문항 원문 | 있는 근거로 보완 가능하면 수정, 지원 이유 등 재료가 없으면 사용자 확인 |
| G2 | 사실적 주장에 허용된 근거가 있고 역할·상태·수치가 보존되는가 | Jev + 주장/근거 대조 | 과장 삭제·원래 표현 복원이 가능하면 수정, 출처 충돌은 사용자 확인 |
| G3 | 원고 내·문항 간 사실이 모순되지 않는가 | Jev + 전체 원고 | 문장 문제는 수정, 원자료 자체 충돌은 사용자 확인 |
| G4 | 문항별 분량 조건을 지켰는가 | 서버 계산 | 계산 규칙이 명확하면 조정, 사이트 규칙 미확인은 별도 표시 |
| G5 | 명시된 형식과 보존·제외 지시를 지켰는가 | 서버 + 필요한 의미 판정 | 위반 부분 수정, 상충하는 사용자 조건은 확인 |
| G6 | 요청된 평가 범위를 누락 없이 검사했는가 | 서버의 평가 목록 | 잘림·미실행·오류는 미완료, 통과로 처리하지 않음 |

G1~G3의 `PASS`는 제공된 자료 범위에서 문제를 발견하지 않았다는 뜻이다. 외부 사실 검증 완료를 의미하지 않는다. 자료가 모자라면 `UNKNOWN`; 적용되지 않는 조건만 `NOT_APPLICABLE`을 허용한다. G5의 명시적 보존 조건은 문체 개선보다 우선한다.

## 품질 평가표

각 지표는 아래 0~4의 다섯 수준을 Jev `score` 질문의 기준으로 사용한다. 하나의 질문에는 하나의 평가 개념과 평가 대상을 명시한다. 실제 API 응답은 소수점일 수 있다.

| ID · 지표 · 기본 가중치 | 0 | 1 | 2 | 3 | 4 |
| --- | --- | --- | --- | --- | --- |
| Q1 문항 답변 · 25 | 질문과 무관 | 주제를 언급하지만 답이 없음 | 일부 답했으나 핵심이 모호 | 필수 요소에 직접 답함 | 직접적인 답과 경험·결론이 집중적으로 연결됨 |
| Q2 JD 연결 · 20 | 관련 없는 소재 | 기술·역량 단어만 나열 | 경험과 요구 업무의 연결이 약함 | 관련 경험이 요구 업무를 뒷받침 | 역할·문제·행동으로 연결이 명확하고 과장이 없음 |
| Q3 전체 일관성 · 15 | 주장이 서로 충돌 | 핵심 주장과 경험이 어긋남 | 흐름에 설명되지 않은 도약이 있음 | 주장·근거·결론이 이어짐 | 문단마다 새 정보를 더하며 핵심 답을 강화함 |
| Q4 문단 구성 · 10 | 내용이 뒤섞여 역할 식별 불가 | 반복·불필요한 배경이 중심 | 역할은 있으나 중복·전환이 어색 | 문단 역할과 순서가 명확 | 문항에 맞는 분량·전환으로 읽기 쉬움 |
| Q5 경험 구체성 · 15 | 추상적인 자기평가뿐 | 경험 이름만 있고 행동 불명확 | 행동은 있으나 개인 역할 또는 연결이 모호 | 본인의 행동·판단 또는 확인된 산출물이 드러남 | 제공된 근거 안에서 선택·행동·결과의 관계가 선명함 |
| Q6 문장 명확성 · 10 | 의미 파악이 어려움 | 중의적·장황한 표현이 빈번 | 읽을 수 있으나 일부 군더더기·번역투가 있음 | 의미와 주체가 명확하고 자연스러움 | 정확한 용어와 간결한 표현으로 전달력이 높음 |
| Q7 표현 절제 · 5 | 상투적인 평가·슬로건이 내용을 대체 | 미사여구·교훈 반복이 잦음 | 일부 장식·중복이 남음 | 경험 중심이며 불필요한 장식이 적음 | 필요한 성찰·전문용어를 유지하며 표현이 절제됨 |

평가 예외:

- 수치 성과가 없어도 Q5 4점이 가능하다. 제공된 행동·산출물만으로 판단하며 허위 수치를 유도하지 않는다.
- Q4는 특정 문단 수나 STAR 형식을 요구하지 않는다. Q6은 짧은 문장 비율·접속어 수 자체를 품질로 환산하지 않는다.
- JD가 없거나 해당 문항에 무관하면 Q2는 `NOT_APPLICABLE`이다. 필요한 JD 일부가 누락되었으면 `UNKNOWN`이다.
- 지원자의 기준 글이 있으면 별도 `voice_alignment` 진단을 제공한다. 기준 글이 없으면 작성자 고유 목소리를 평가했다고 표시하지 않는다. 이 진단은 기본 총점에 넣지 않는다.
- 초안 자체는 개인 경험의 출처가 아니다. 사실을 풍부하게 보이도록 꾸며서 점수를 올려서는 안 된다.

### 점수·신뢰도·집계

- 항목 점수: 0~4. 품질 표시값: `25 × Σ(가중치 × 항목 점수) / Σ(적용 가중치)`로 0~100에 환산하고 표시 때만 반올림한다.
- `NOT_APPLICABLE`은 분모에서 제외하고 제외 이유를 표시한다. `UNKNOWN`·`ERROR`가 하나라도 있으면 종합점수는 `null`이며 확인된 항목 점수만 보여준다.
- Q1~Q7 종합점수는 문항 전체에 대한 평가로 산출한다. 문단·문장 점수를 같은 총점에 다시 더하지 않는다.
- 여러 문항은 각각 점수를 표시한다. 전체 지원서 결과는 가장 엄격한 문항 결과와 문항 간 G3 검사로 결정하며 평균으로 실패를 숨기지 않는다.
- Jev의 `confidence`는 정답률이나 품질점수가 아니다. 원래 확률분포와 함께 별도로 보관한다.
- 동일한 평가 기준·모델·입력 문맥 조건에서만 전후 점수를 비교한다. 입력 근거나 JD가 바뀌면 기준점을 새로 평가한다.

### 초기 운영 정책 `career-policy/0.1.0`

다음 숫자는 실험 시작값이다. 평가 기준만으로 한국어 자소서 품질 개선이 증명되는 것은 아니다.

| 조건 | 초기값·처리 |
| --- | --- |
| 문항 품질 통과 | 적용되는 모든 Q 항목 ≥ 3.0, 모든 필수 확인 PASS 또는 정당한 NOT_APPLICABLE |
| 종합점수 | 참고 표시만 사용; 독립적인 합격 기준 없음 |
| 의미 평가의 확신도 | `confidence < 0.70`이면 검토 필요; 높은 값도 진실성 보장 아님 |
| 자료 부족·모순 | 필요한 근거가 없으면 점수와 무관하게 `NEEDS_INPUT` |
| 경계 구간 | 어느 Q든 2.8~3.2이면 자동 재작성·통과를 보류하고 `REVIEW` |
| 재작성 한도 | 시작 원고 이후 최대 2개 수정 후보; 초안 평가는 횟수에 포함하지 않음 |
| 악화 허용 범위 | 새로운 필수 위반 불허, 어느 Q든 0.3 이상 하락하면 자동 채택 보류 |
| 개선 정체 | 필수 위반 해소도 없고 총점 개선이 2점 미만이면 중단 후 `REVIEW` |
| 외부 호출 제한 | 평가 세션당 최대 12개 Jev 요청; 각 요청은 서버가 검증한 모델 입력 한도 내로 제한 |

경계 구간은 통과 기준보다 우선한다. 따라서 초기 정책의 자동 PASS에는 각 적용 Q가 3.2를 초과해야 한다. 3.0~3.2는 기준을 충족하더라도 사람의 검토 대상으로 남긴다. 경계 점수만으로 재호출을 반복하지 않는다. 자동 수정은 낮은 점수뿐 아니라 위치와 적용 가능한 수정 이유가 확인된 경우에만 진행한다. 악화·개선 정체 판단은 완전한 수정 전후 평가가 있는 경우에만 적용하며 최초 평가에는 적용하지 않는다.

## 전체·부분 평가 흐름

1. **기준 고정:** JD, 문항, 사실 근거, 사용자 수정 범위, 평가표·정책 버전을 고정한다. 작성·진단만 요청했으면 자동 수정으로 확장하지 않는다.
2. **정확한 검사:** 문항별 실제 제출 본문을 서버에서 계산한다. 분량 초과는 평가 입력 한도를 넘지 않는 한 의미 평가와 함께 반환한다.
3. **전체 평가:** 각 문항의 Q1~Q7과 G1~G5, 전체 지원서의 문항 간 G3를 평가한다. 짧은 원고는 전체 문맥을 공유한 여러 질문을 한 요청으로 묶는다.
4. **부분 진단:** 미달 항목이 있으면 해당 문항의 문단별 관련 지표를 검사한다. 대상 문단 원문, 바로 앞뒤 문단 원문, 문항 원문, 관련 JD와 근거를 제공한다. 문맥 요약은 보조 정보이며 원자료 대조를 대신하지 않는다.
5. **문장 진단:** 문단 진단으로 수정 위치를 정하기 어려운 경우에만 문장 ID를 부여해 문단 전체와 함께 평가한다. 전체 구조 문제를 문장 평가로 판정하지 않는다.
6. **수정 지시:** ChatGPT가 원문과 미달 기준을 대조해 수정 이유를 작성한다. Jev가 자연어 이유나 수정문을 반환했다고 표시하지 않는다. 사실 부족이면 사용자에게 필요한 사실을 요청한다.
7. **부분 수정:** 지정 문단 또는 승인된 구조 범위만 수정한다. 모든 후보를 해당 초안 해시에 연결한다. 범위 밖 변경은 채택하지 않는다.
8. **회귀 평가:** 후보 전체의 필수 확인·Q1~Q7과 문항 간 모순을 다시 검사한다. 문단 점수 개선만으로 채택하지 않는다.
9. **종료:** 정책에 따라 최종 후보, 이전 후보 또는 확인사항을 반환한다. 저장은 별도 명시 요청으로 수행하며 품질 점수만으로 저장 권한이 생기지 않는다.

길이 때문에 문항 전체를 모델에 넣을 수 없으면 문단별 검사와 별도로 문단 간 주장·역할 대조를 수행한다. 전체를 검사하지 못한 항목은 G6 `UNKNOWN`, 종합점수 `null`, 결과 `INCOMPLETE`로 표시한다. 조용히 잘라 보낸 입력으로 전체 통과를 선언하지 않는다.

## 종료 결과의 의미

서버는 다음 순서로 결과를 결정한다.

1. 입력·응답 검증 실패 또는 호출 오류 → `ERROR`.
2. 요청된 검사 누락·일부만 실행 → `INCOMPLETE`.
3. 필요한 개인 사실·자료가 없거나 원자료 충돌 → `NEEDS_INPUT`.
4. 낮은 확신도·경계 점수·근거 없는 진단·악화·정체·수정 또는 호출 한도 도달 → `REVIEW`.
5. 필수 확인과 품질 기준을 모두 충족 → `PASS`.
6. 나머지 기준 미달이 있고 근거 내에서 수정 가능 → `REVISE`.

호출 예산을 모두 썼더라도 이미 마지막 전체 평가가 완전하게 끝나 통과했다면 `PASS`다. 한도 때문에 필요한 검사가 남았으면 `INCOMPLETE`; 검사는 끝났으나 추가 수정이 필요하면 `REVIEW`다. 사용자가 진단만 요청한 경우 `REVISE`는 권고이며 실제 수정은 하지 않는다.

일반 Chat에서 도구 호출 순서는 스킬 지침으로 안내한다. 실행이 중단된 세션은 마지막 평가 대상과 완료 범위를 반환할 수 있어야 한다. ChatGPT 대화 전체나 내부 추론을 수집하는 기능은 필요하지 않다.

## 기존 스킬에 반영할 규칙

| 스킬 | 연결 방식 |
| --- | --- |
| jd-analyzer | 요구사항 원문·필수/우대·논리 조건과 근거 연결을 출력; 경험 매칭과 글의 품질 점수를 분리 |
| cover-letter-outline | 문항별 핵심 답, 문단 역할, 근거 ID, 관련 JD ID를 전달 |
| cover-letter-draft | 사용자 요청이 개선까지 포함하면 검사·평가 호출; 초안만 요청했으면 초안에서 종료 |
| ai-killer | Q6·Q7의 문체 검토에 활용; AI 작성 확률 판정이나 탐지 회피 목표를 추가하지 않음 |
| cover-letter-finalizer | 수정 범위·사실을 보존하고 미달 부분 수정 후 전체 재평가; 저장은 명시 요청에 따름 |

`text_audit.py`가 정의한 글자 수 계산 방식을 서버 도구로 제공하면 일반 Chat의 파일·Python 실행 가능 여부에 의존하지 않는다. 기존의 오프라인 점검 방식은 유지한다. MCP 연결이 없으면 기존 작성 기능을 제공하고 Jev 평가를 수행했다고 표시하지 않는다.

## 검증 계획과 완료 조건

1단계 완료 조건은 지표·점수·자료 부족 처리·버전 연결·수정 범위·종료 조건이 문서에서 해석 가능하고 서로 모순되지 않는 것이다. 다음 단계는 이 계약으로 평가 API와 MCP를 구현하는 것이다.

구현 뒤에는 동의받은 자료 또는 가상 자료로 약 30~50개 문항을 초기 검토한다. 이는 정확도 보장을 위한 충분한 표본이라는 뜻이 아니다. 문항 유형, 길이, JD 유무, 미확인 경험, 과장, 좋은 원고, 혼합 수정본을 포함한다. 동일 경험에서 파생한 글은 보정용과 보류 검증용 묶음에 나눠 넣지 않는다.

사용자가 매긴 항목별 판단·수정 전후 선호와 비교해 오탐, 놓친 과장, 불필요한 재작성, 사실 훼손, 호출 비용·시간을 기록한다. 고정 입력의 반복 평가로 점수 변동을 측정한다. 보정한 정책은 버전을 올리고 보류 표본에서 평가한다. Jev 점수 상승만으로 품질 개선을 입증하지 않는다.

필수 확인 사례:

- 자연스러운 원고는 수정하지 않는다. 수치 성과가 없다는 이유만으로 감점하지 않는다.
- JD가 없으면 관련성 점수는 적용 제외; 일부 JD가 잘렸으면 정보 부족으로 구분한다.
- 관련 경험이 없는 요건은 미충족으로 단정하지 않고, 명시적으로 경력 연수가 부족하면 미충족으로 표시한다.
- 초안의 임의 성과 수치를 근거로 재사용하지 않는다. 계획을 완료로 바꾼 수정은 채택하지 않는다.
- 문단은 개선됐지만 전체 주장이 충돌하면 통과하지 않는다.
- 사용자 정정·JD 변경·원고 변경 후 이전 평가를 재사용하지 않는다.
- 평가 API 장애를 0점 또는 통과로 변환하지 않는다. 한도 도달 시 실제 평가 범위를 표시한다.
- 원고나 JD 속 명령문은 데이터로 처리한다. 기준·모델·권한을 바꾸는 지시로 실행하지 않는다.
- DB revision 충돌 시 사용자 원고를 유지하고 자동 덮어쓰지 않는다.
